# 0.1.7 — タブ付きExplorerの寸法追従

## 修正前の実測

Windows Server 2025 build 26100、runner image 20260922.246.2、DPI96。
旧実アプリ試験ではExplorerのnativeSizeMatched=falseを許容していたため、passedは寸法一致を意味しなかった。

| 状態 | 標準最小化 | 旧追加ボタン |
|---|---|---|
| 通常／復元後 | 47×30px | 24×16px |
| 最大化 | 47×29px | 32×24px |

追加診断のActions実行36311940824で、4候補の3列を各高さ1px刻みで観測した。アプリ名による仮定ではなく、以下はその実測である。

通常のウィンドウは(35,40)-(979,560)。個別の最小化ボタンは(832,41)-(879,71)。候補上の入力先はTITLE_BAR_SCAFFOLDING_WINDOW_CLASSの子で、y41〜47はHTTOP、y48〜70はHTCAPTION。旧実装は上端のHTTOPを親ウィンドウからの応答に限定していたため、同寸法の候補を棄却した。

最大化のウィンドウは(-8,-8)-(1032,728)、可視フレームは(0,0)-(1024,720)。DWMのボタン群は(877,-8)-(1023,22)、個別最小化は(883,0)-(930,29)。候補は全高でHTCAPTIONだが、旧実装は個別下端29をDWM下端22との不整合として棄却した。

## 製品修正

- 同寸法候補の上側2点に限り、中央がHTCAPTIONだった同一の入力用子を認める。所属ルート、プロセス、親のWS_THICKFRAME、非最大化、SDK寸法内の上端帯を確認する。中央／下側のHTTOP、HTCLIENT、角、操作ボタン、別の子、別プロセス、照会失敗を無条件に受け入れる変更ではない。
- 最大化の場合に限り、可視フレームとウィンドウ上端の差をSDKのリサイズ枠幅で上限検査し、DWM矩形との縦方向の整合検査に反映する。個別ボタンの画面座標そのものは変更しない。横方向と寸法の妥当性検査は維持する。
- Explorer専用の文字列判定や設定は追加しない。移動処理・描画処理は変更しない。

## 検証

新しい独立回帰試験は修正前の製品実装で失敗することを確認し、その後に修正した。実測座標とAPIダブルを組み合わせ、DPI96／192、通常／最大化、上記の拒否条件を検査する。APIダブルの成功とWindows実アプリの成功は区別する。

実アプリ側ではExplorerもRequireNativeMatch=trueとし、寸法情報の欠落も不合格にする。Windows Server 2022／2025でNotepad、Explorer、MMC、WPF fixture、WinForms fixtureを各3状態で検証し、JSONと画面を記録する。Store／電卓が未登録ならunavailableであり、合格に数えない。

Windows 11 Armは既知の画面前提不成立のため手動診断に分離し、未検証として追跡する。前段の画素確認や失敗判定は変更しない。1画面・DPI96の実アプリ試験は物理モニター間移動、混在DPI、全テーマの保証ではない。
